# 엔진 명세

지표 정의와 측정 방법입니다. 과제 구성과 특징 추출은 국내 선행 연구를 따릅니다.

> 전근아, 김휘영 연구팀. *Automated AI based identification of autism spectrum disorder from home videos.* npj Digital Medicine 8:607 (2025).
> [초록](https://www.nature.com/articles/s41746-025-01993-5) · [전문](https://pmc.ncbi.nlm.nih.gov/articles/PMC12514021/)
> 국내 9개 상급종합병원, 510명(ASD 253 / TD 257), 18~48개월.

## 논문에서 가져오는 것과 가져오지 않는 것

이 구분을 넘어서 말하면 심사에서 깨집니다.

| 가져온다 | 가져오지 않는다 |
|---|---|
| 과제 구성 3개 | 모델·코드 (비공개) |
| 특징 정의 (반응 지연, 유도 횟수, 소유권 전환) | AUROC 0.83 / 정확도 75% |
| 촬영 프로토콜 (시야 밖 호명, 5초 재호명) | 510명 임상 검증 |
| 참조값 (TD 반응 지연 3.62초, SD 3.25) | 분류·판정 |
| 저자들이 밝힌 실패 지점 | 그들의 측정 정확도 |

**우리 구현의 정확도는 우리가 입증합니다.** 논문 성능은 그들 모델의 숫자입니다. 우리는 분류기를 만들지 않으므로 판별 정확도가 품질 기준이 아니고, **재현성**이 유일한 품질 기준입니다(§6).

## 1. 과제 구성

| `TaskType` | 과제 | 측정값 | 필요 모델 |
|---|---|---|---|
| `name_response` | 호명반응 | 반응 지연(초) | Pose + Face |
| `imitation` | 동작 모방 | 모방까지의 지연(초) | Pose |
| `ball_play` | 공 주고받기 | 전달 성공·전달 시간(초) | Pose + ObjectDetector |

여기에 과제와 무관하게 모든 영상에서 계산되는 **공통 지표**가 붙습니다(§3).

### 기존 `TaskType`에서의 변경

```
gross_motor  →  imitation      (독립 서기 → 동작 모방)
fine_motor   →  ball_play      (블록 쌓기 → 공 주고받기)
social       →  name_response  (이름 동일, 값만 변경)
```

영향 범위 — 이 네 곳만 고치면 됩니다.

- `src/types/analysis.ts` — `TaskType` 유니온
- `src/engine/analyzeVideo.ts` — switch 분기
- `src/engine/metrics/` — 파일명 `grossMotor/fineMotor/social` → `nameResponse/imitation/ballPlay`
- `src/data/mockNorms.ts` — 키 변경 (단, §7 참고)

라우트(`/task-guide/:taskType` 등)는 문자열만 바뀌므로 `App.tsx`는 수정 불필요합니다.

### 영역 매핑이 사회성으로 쏠립니다 — 확인 필요

논문 과제 셋은 전부 사회적 상호작용을 봅니다. 자폐 선별 연구이기 때문입니다.

| 과제 | K-DST 영역 |
|---|---|
| 호명반응 | 사회성 |
| 동작 모방 | 사회성(모방) + 대근육(팔 들기) |
| 공 주고받기 | 사회성(상호작용) + 대근육(굴리기) |

**독립 서기가 빠지면서 순수 대근육 지표가 없어집니다.** 제안서에 "발달 전반"으로 써 둔 서술을 "상호작용 중심 기록"으로 좁히거나, 독립 서기를 네 번째 과제로 남길지 팀에서 정해야 합니다.

## 2. 공통 — 사람 식별

`PoseLandmarker`를 `numPoses: 2`로 실행합니다. 논문은 17개 COCO 키포인트를 썼고, MediaPipe의 33개는 그 상위집합입니다.

쓰는 인덱스: `0` 코, `7/8` 귀, `11/12` 어깨, `13/14` 팔꿈치, `15/16` 손목, `23/24` 엉덩이, `25/26` 무릎, `27/28` 발목.

두 사람이 검출되면 **바운딩박스 높이가 큰 쪽을 보호자, 작은 쪽을 아이로** 식별합니다. 한 명만 검출되면 아이로 봅니다.

식별은 프레임마다 다시 하지 않습니다. **최초 3초의 다수결로 한 번 정하고 이후 바운딩박스 IoU로 추적**합니다. 추적이 끊기면 다시 다수결로 정합니다.

### 머리 방향 (gaze vector)

논문은 별도 시선 추정 모델 없이 키포인트에서 머리 방향을 근사했습니다. **양쪽 귀를 잇는 축에 직교하고 코를 지나는 선**입니다. 2D에서는 이렇게 씁니다.

```
earMid = (P7 + P8) / 2
g      = normalize(P0 - earMid)      // 머리가 향한 방향
```

유효 프레임 조건: 코 visibility ≥ 0.5, 양쪽 귀 중 하나 이상 visibility ≥ 0.5.

호명반응 과제에서는 더 정확한 각도가 필요하므로 `FaceLandmarker`의 `outputFacialTransformationMatrixes`로 yaw를 직접 뽑습니다.

## 3. 지표 구조

지표를 3군으로 나눕니다. 1군과 2군이 MVP 범위입니다.

| 군 | 내용 | 자동 측정 | 종단 그래프 |
|---|---|---|---|
| **1군 — 공통 지표** | 보호자 지향 시간 · 활동량 · 신체 접촉 | O — 모든 영상 | 선 2개 (접촉 제외) |
| **2군 — 과제 지표** | 호명반응 지연 · 모방 지연 · 공 전달 시간 | O — 해당 과제 영상 | 시점 마커 |
| **3군 — 측정하지 않는 영역** | 언어 · 인지 · 자조 | X | 없음 |

핵심은 **1군이 과제와 무관하게 모든 영상에서 나온다**는 점입니다. 2군은 발달 창을 벗어나면 포화되지만 1군은 포화되지 않으므로, 끊기지 않는 종단 축은 1군입니다.

### 1군 — 공통 지표 (ambient)

논문에서 **과제별 지표보다 신호가 강했던** 세 지표입니다.

| 과제 | 과제 지표만 | 공통 지표 추가 |
|---|---|---|
| 동작 모방 | AUROC 0.65 | **0.75** |
| 공 주고받기 | AUROC 0.62 | **0.78** |

군 간 차이도 공통 지표가 더 컸습니다 — 눈맞춤 결여 p<0.001, 비관여 움직임 p<0.001, 신체 접촉 p=0.026. 반면 과제 지표 중에서는 호명반응 지연(p=0.017)만 유의했고 나머지는 유의하지 않았습니다.

구현은 가장 쉽습니다. **임계값도 분류기도 없고 누적 초만 셉니다.** `engine/metrics/ambient.ts` 하나로 만들고 세 과제가 공유합니다.

### 3-1. 보호자 지향 시간 `caregiverOrientSec`

```
t = normalize(caregiverHead - childNose)
oriented = dot(g_child, t) >= 0.3        // 약 72도 콘 이내
```

- 유효 프레임 조건 + 보호자 머리 검출됨
- 프레임 판정은 떨리므로 **0.3초 이동 중앙값으로 평활**한 뒤 누적
- 분모는 전체 길이가 아니라 **두 사람이 모두 검출된 구간**(`bothInFrameSec`)

논문의 "눈맞춤 결여"를 양의 방향으로 뒤집은 것입니다. 결여 시간을 세면 화면에 쓸 때 판정처럼 읽힙니다.

### 3-2. 활동량 `activitySec`

아이 랜드마크의 min/max 바운딩박스를 씁니다. 둘 중 하나라도 만족하면 움직임 프레임입니다.

- 중심 이동량 / 박스 대각선 > **0.02**
- 가로세로비 변화율 > **0.05**

가로세로비를 함께 쓰는 이유는 제자리에서 앉았다 일어서는 움직임이 중심 이동을 거의 만들지 않기 때문입니다. **0.3초 이동 평균으로 평활** 후 누적. 분모는 아이가 검출된 전체 구간.

### 3-3. 신체 접촉 시간 `contactSec`

보호자 손목(`15`/`16`) 중 하나가 아이 바운딩박스 안에 있으면 접촉입니다. **0.3초 이상 연속**인 구간만 셉니다(스침 제외).

**이 값은 종단 그래프에 올리지 않습니다.** 자유 상호작용 중의 접촉은 애정 표현이고 과제 중의 접촉은 보호자의 물리적 유도입니다. 맥락에 따라 의미가 뒤집히므로 참고값으로만 둡니다.

### 3군 — 자동 측정하지 않는 영역

언어·인지·자조는 영상에서 측정하지 않습니다. K-DST 6영역 중 세 영역이고, 영상만으로 수치화할 수 없습니다.

그렇다고 없는 것처럼 두지는 않습니다. **과제 안내와 영상 보관까지만 합니다.**

- 보호자는 해당 월령의 관찰 거리를 안내받고 영상을 남긴다
- 앱은 그 영상에 지표를 붙이지 않는다
- 진료 요약에는 "영상 있음"으로만 표시한다

측정값이 없는 영역을 억지로 수치화하면 측정한 것보다 넓은 주장을 하게 됩니다.

다만 **1군은 이 영상들에서도 계산됩니다.** 보호자와 아이가 함께 프레임에 있으면 과제가 무엇이든 세 값이 나옵니다. 3군 영역도 완전히 비어 있지는 않다는 뜻이고, 이게 1군을 둔 이유 중 하나입니다.

### 단일 측정값을 믿지 않는다

1군은 아이 기분·시간대·장소에 따라 흔들립니다. 2군보다 노이즈가 큽니다.

**종단 그래프에는 단일 측정값이 아니라 최근 3회의 중앙값을 그립니다.** 측정이 3회 미만이면 그래프 대신 `기록이 3회 이상 쌓이면 변화를 보여드립니다 (현재 N회)`를 둡니다. 개별 측정값은 세션 상세에서만 봅니다.

세션 상세에는 **촬영 조건**을 함께 표시합니다. 같은 조건끼리만 비교되고 있는지 보호자와 의사가 판단할 수 있어야 합니다.

### 지표에 이름을 붙이는 원칙

측정한 것을 그대로 부릅니다. 호명반응에서 측정하는 것은 **머리 방향**이므로 "눈맞춤"이나 "사회적 반응"이라고 부르지 않습니다. 1군의 첫 지표도 "눈맞춤 시간"이 아니라 **보호자 지향 시간**입니다.

측정한 것보다 넓은 이름을 붙이면 판정으로 읽힙니다.

## 4. 2군 — 과제별 측정

### 4-1. `name_response` — 호명반응

**프로토콜 (논문 그대로)**

보호자가 **아이 시야 밖에서** 이름을 부릅니다. 5초 안에 반응이 없으면 다시 부르거나 익숙한 소리를 사용할 수 있습니다. 반응은 발성이든 행동이든 인정합니다.

**자극 시점**

논문은 음성 인식(Whisper)으로 호명 시점을 잡았고, **보호자 발화의 변이 때문에 반응 시점에 오차가 생겼다고 한계로 밝혔습니다.**

우리는 뒤집습니다. **앱이 "삐" 신호음을 내고 그 시각을 `stimulusTimestamp`로 기록**합니다. 보호자는 소리를 듣고 바로 이름을 부릅니다.

- 앱이 자기가 만든 시점을 쓰므로 시점 오차가 없습니다
- 엔진 계약은 바뀌지 않습니다 — `stimulusTimestamp`(ms, 녹화 시작 기준) 그대로
- **오디오 처리를 구현하지 않습니다.** 발성 반응은 측정하지 않고 행동 반응만 봅니다

**절차**

1. 3초 카운트다운
2. 신호음 → `t0` 기록
3. 이후 10초간 `FaceLandmarker`에서 yaw를 프레임마다 추출
4. yaw 각속도가 **30도/초**를 초과하는 첫 프레임을 `t1`
5. `t0` 이후 yaw 변화량 절댓값이 **25도 이상**이면 반응으로 인정
6. 5초 안에 반응 없으면 신호음 재생. **최대 3회**

**산출**

```ts
{
  latencySec?: number;   // t1 - t0, 최초 신호 기준
  responded: boolean;
  attempts: number;      // 1~3
  yawDeltaDeg?: number;
}
```

`attempts`는 지표가 아니라 맥락 정보입니다. 그래프에 올리지 않습니다(논문에서 p=0.101로 유의하지 않았습니다).

**참조값** — 일반 발달 아동 3.62초(SD 3.25), 18~48개월. 화면에 "참고"로만 표시하고 비교 판정 문구는 붙이지 않습니다.

**무효** — 10초 구간에서 얼굴 검출 프레임이 **70% 미만** → `'아이 얼굴이 충분히 보이지 않았습니다'`

### 4-2. `imitation` — 동작 모방

**프로토콜 (논문 그대로)**

보호자가 단순 동작을 시범 보입니다. **손 들기**와 **박수**입니다. 여러 번 유도할 수 있습니다.

**팔 들기 검출** — 논문은 손목·팔꿈치·어깨의 Y축 정렬, 팔꿈치–어깨 각도, 팔꿈치–손목 벡터 규칙을 썼습니다. 구체화하면:

```
// 이미지 좌표는 y가 아래로 증가
raised = wrist.y < elbow.y - 0.02        // 손목이 팔꿈치보다 위
      && elbow.y < shoulder.y + 0.05     // 팔꿈치가 어깨 근처 이상
      && angle(shoulder→elbow, vertical) >= 30도
```

좌우 중 한쪽이라도 만족하면 팔 들기입니다. **0.3초 이상 연속** 유지된 경우만 인정합니다.

**박수 검출**

```
dist(P15, P16) / shoulderWidth < 0.35    // 두 손목이 가까움
```

**1초 안에 접근–분리가 2회 이상** 반복되면 박수로 봅니다.

**산출**

```ts
{
  imitated: boolean;
  latencySec?: number;   // 보호자 동작 시작 → 아이 모방
  attempts: number;      // 보호자 유도 횟수
  actionType?: "arm_raise" | "clap";
}
```

**보호자 동작 시작 시점**을 어떻게 잡는지가 관건입니다. 두 방법 중 하나입니다.

1. **호명반응과 같이 신호음** — 앱이 신호를 내고 보호자가 바로 시범. 시점 오차 없음. **이쪽을 권합니다**
2. 보호자 키포인트에서 팔 들기를 검출해 그 시점을 쓰기 — 자동이지만 보호자 자세 추정이 아이보다 안정적이라는 전제가 필요

논문이 보고한 **키포인트 오류가 이 과제에서 가장 많았습니다.** 단일 프레임으로 판정하지 않고 0.3초 연속 조건을 두는 이유입니다.

**무효** — 아이 상반신 랜드마크 평균 visibility < **0.5**

### 4-3. `ball_play` — 공 주고받기

**프로토콜 (논문 그대로)**

보호자가 공을 아이에게 굴려 주고받습니다. **공은 보호자와 아이 사이에 둡니다.** 비언어적 제스처로 시작하고 필요하면 언어적 격려를 추가합니다.

**공 검출 — 논문이 한계로 밝힌 지점입니다**

저자들은 COCO 사전학습 검출기(YOLOv8)를 썼고 **공 검출이 일관되지 않았다고 보고했습니다.** 9개 병원에서 보호자가 아무 공이나 썼기 때문입니다.

우리는 세 가지로 줄입니다.

1. **`ObjectDetector` (MediaPipe Tasks Vision)** — EfficientDet-Lite0, COCO 학습, `sports ball` 클래스 포함. 이미 쓰는 `tasks-vision` 패키지 안에 있어 새 인프라가 필요 없습니다. 모델 약 5MB
2. **색 기반 폴백** — 검출이 끊기면 HSV 색 블롭 추적. 공 색을 알고 있으므로 일반 검출보다 안정적입니다
3. **촬영 가이드로 공을 규정** — `밝은 단색 공(지름 10~20cm)을 준비해 주세요`. **논문은 통제할 수 없었지만 우리는 가이드를 쓰는 쪽이라 통제할 수 있습니다**

이게 심사에서 쓸 수 있는 답이기도 합니다 — 선행 연구가 실패한 변수를 우리가 어떻게 줄였는지.

**소유권과 전달 (논문 정의)**

```
owner = argmax IoU(ballBox, personBox)   // child | parent | none
```

- **유효 상호작용** = 소유권이 `child → parent`로 순차 전환된 경우
- **전달 시간** = 아이가 공을 가진 시점부터 보호자로 전환된 시점까지

**산출**

```ts
{
  transferred: boolean;
  transferTimeSec?: number;
  transferCount: number;
  ballDetectedRatio: number;   // 공이 검출된 프레임 비율
}
```

**무효** — `ballDetectedRatio` < **0.5** → `'공이 화면에 충분히 보이지 않았습니다'`

세 과제 중 난도가 가장 높으므로 **마지막에 구현**합니다. 공통 지표(§3)만으로도 이 과제의 영상은 의미가 있습니다 — 논문에서도 공놀이 과제는 과제 지표 0.62에서 공통 지표를 더해 0.78로 올랐습니다.

## 5. 인터페이스 변경

`docs/interface.md`의 계약을 이렇게 확장합니다. **`analyzeVideo` 시그니처는 그대로**입니다.

```ts
export type TaskType = "name_response" | "imitation" | "ball_play";

export interface AnalysisInput {
  videoBlob: Blob;
  taskType: TaskType;
  stimulusTimestamp?: number;   // name_response, imitation: 신호음 재생 시점(ms)
}

export interface AnalysisResult {
  status: "success" | "retry_needed";
  retryReason?: string;

  metric?: {
    value: number;
    unit: "seconds" | "count";
    label: string;
  };

  ambient?: {                    // 추가 — 모든 과제에서
    bothInFrameSec: number;
    caregiverOrientSec: number;
    activitySec: number;
    contactSec: number;
  };

  detail?: Record<string, number | boolean | string>;   // 과제별 원시값
}
```

`metric`은 화면에 크게 띄울 대표값 하나입니다. 과제별 원시값은 `detail`에 담고 세션 상세 화면에서 봅니다.

`ambient`는 두 사람이 프레임에 있을 때만 채워집니다. **호명반응은 보호자가 시야 밖이므로 비어 있는 게 정상**입니다 — 프론트는 `undefined`를 정상 상태로 처리해야 합니다.

## 6. 재현성 — 우리가 입증해야 하는 것

판정하지 않으므로 판별 정확도가 품질 기준이 아닙니다. **같은 것을 재면 같은 값이 나오는가**가 기준입니다.

데모 기간에 실제로 측정할 수 있고, 아이 영상이 없어도 성인으로 됩니다.

| 측정 | 방법 | 보고할 값 |
|---|---|---|
| 분석 재현성 | 같은 영상 10회 분석 | 표준편차 |
| 촬영 재현성 | 같은 장면 3회 촬영 | 변동 폭 |
| 외부 타당도 | 사람이 스톱워치로 센 값과 비교 | 평균 절대오차 |

`src/dev/EngineTest.tsx`에 이미 개발용 화면이 있으니 거기에 붙입니다.

**심사에서 "신뢰할 수 있나요"를 물으면 이 숫자로 답합니다.** 논문 과제를 쓴다는 것만으로는 우리 구현의 정확도가 설명되지 않습니다.

## 7. 쓰지 않는 것

- **분류·판정** — 자폐 여부, 위험도, 등급
- **또래 비교** — `mockNorms.ts`의 `compareToNorm()`은 `"good" | "average" | "attention"`을 돌려주고 `/doctor/patients/:id`에서 쓰입니다. 표현 규칙과 충돌하고, 테이블 값의 출처도 없습니다. 제거 또는 "참고값" 성격으로 재설계가 필요합니다
- **오디오 처리·음성 인식** — 논문이 시점 오차를 보고한 지점입니다
- **발성 반응** — 행동 반응만 측정합니다
- **영상의 네트워크 전송** — 지표값만 공유합니다

## 8. 구현 순서

| 단계 | 내용 | 완료 조건 |
|---|---|---|
| 1 | `PoseLandmarker` 2인 검출 + 사람 식별 | 두 사람에 스켈레톤이 각각 붙고 fps 20 이상 |
| 2 | **`ambient.ts` 공통 지표 3종** | 영상 파일 입력에 세 값이 나오고, 같은 영상 재입력 시 1초 이내 재현 |
| 3 | `name_response` | 신호음 후 고개 돌리면 지연이 초로 나옴. 얼굴 가리면 무효 |
| 4 | `imitation` | 팔 들기와 박수가 각각 검출됨 |
| 5 | `ball_play` | `ObjectDetector`로 공 추적, 소유권 전환 검출 |
| 6 | 재현성 측정 (§6) | 세 수치를 표로 보고 |

**공통 지표를 2단계에 두는 이유**는 가장 쉽고(누적 초만 셈), 세 과제가 공유하며, 종단 그래프의 기본 축이라 가장 먼저 필요하기 때문입니다. 과제 지표가 하나도 없어도 공통 지표만으로 그래프가 그려집니다.
